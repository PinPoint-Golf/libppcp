## 1. The decision, in one line

**X25519 does not live in `libppcp`. The two values that need it are *parameters*, exactly as `psk`, `sid`, `rn` and `rn2` already are.**

Each application computes them with the cryptography it already links — OpenSSL on the host, CryptoKit on the device — and passes 32 octets in. `libppcp` does the rest, and its dependency list does not change.

---

## 2. Why a parameter and not a callback

PinPointStudio's finding proposed a callback, mirroring `ppcp_rv_random_fn`. That was the right instinct and the wrong precedent, and the reason is in `include/ppcp/rv.h`'s own header comment:

> *"Storage, and a random number generator. **Every random value below is a PARAMETER.**"*

A callback is right when the library needs something it cannot produce **during a loop it owns**. That is exactly why [5.3a1](../specification/ppcp-rv.md#53-psk-identity)'s rejection sampling takes one: `ppcp_rv_psk_identity_draw()` may need to draw `rn2` several times and only the library knows when to stop.

**Key agreement has no loop.** The component holding the private scalar already has it, and already has the counterpart's public key off the wire. It computes `Z` once. There is nothing to call back for.

Three things follow, and the third is the one worth having:

1. **No new plumbing.** No function pointer, no `void *ctx`, no shared lifetime.
2. **No dependency change.** `libppcp` stays as [plan A1](../implementation/implementation-plan.md) requires it.
3. ⛔ **The whole derivation becomes a pure function, so [§10.4](../specification/ppcp-rv.md#104-guided-pairing) is testable by a build that cannot do curve arithmetic at all** — feed in the published `Z` and every row below it must reproduce. That puts [RT-18](../specification/ppcp-rv.md#9-conformance) in the **one component both applications share**, rather than twice over in two applications that would then be agreeing with themselves, which is [B7](../specification/ppcp-rv.md#annex-b--open-issues) exactly.

This is the same split as [plan A7](../implementation/implementation-plan.md) (TLS lives in the applications) and [A8](../implementation/implementation-plan.md) (discovery lives in the applications), for the same reason.

## 3. Who does what

| | `libppcp` | PinPointStudio | PinPointCapture |
|---|---|---|---|
| Generate the 32-octet private scalar | — | CSPRNG ([7.2a](../specification/ppcp-rv.md#72-handling-the-pairing-secret)) | CSPRNG ([7.2a](../specification/ppcp-rv.md#72-handling-the-pairing-secret)) |
| `pk` from the scalar | — | `EVP_PKEY_new_raw_private_key` | `Curve25519.KeyAgreement.PrivateKey.publicKey` |
| `Z` = agreement | — | `EVP_PKEY_derive` | `sharedSecretFromKeyAgreement` |
| Report agreement failure as `invalid_key` | checks the **zero** half | checks the **failed-call** half | checks the **throw** half |
| Commitment, `BK`, SAS, `K_c`, MACs, `sid`, `PRK`, `K_tls`, `K_id` | **all of it** | — | — |
| Erase the scalar and `Z` | — | ✅ | ✅ |
| Sockets, TLS, mDNS, screens | — | ✅ | ✅ |

⚠ **[11.11f](../specification/ppcp-rv.md#1111-where-x25519-comes-from) splits across the boundary and neither side can do it alone.** A small-order key is rejected by OpenSSL as a *failed call* and by CryptoKit as a *throw*, and something else may yet return an all-zero `Z` — that was [E36](../specification/ppcp-core.md#errata-after-revision-9), measured on both platforms. The library can only see the zero; the application can only see the failure. **Both map to `invalid_key`, neither is a transport error, and neither is retried** — a rejected key is an attack signal and a retry loop eats [3.7b](../specification/ppcp-rv.md#37-the-bootstrap-window)'s single-attempt bound, which is what [§11.8](../specification/ppcp-rv.md#118-what-the-comparison-proves)'s whole argument rests on.

## 4. The agreed surface

To be added to `include/ppcp/rv.h` when RV-6 is built. **Not present today.**

```c
/* -------------------------------------------------- RV-6 bootstrap (RV §11) */

#define PPCP_RV_BS_KEY_BYTES 32   /* pk, the private scalar and Z (11.11a) */
#define PPCP_RV_BS_CT_BYTES  32   /* the commitment, SHA-256 (11.5b)       */
#define PPCP_RV_BS_MAC_BYTES 16   /* mac_i / mac_a, truncated (11.5f)      */

/* X25519 IS NOT HERE AND NEVER WILL BE — RV 11.11, and the same split as
 * plan A7 and A8.  Two values in RV §11 need key agreement, a peer's own
 * public key and the shared secret Z, and both are PARAMETERS exactly as psk,
 * sid, rn and rn2 already are.  The embedding computes them with the crypto
 * it already links.  Everything below is SHA-256, HMAC and HKDF, which this
 * library carries, so plan A1's "no dependencies" is untouched.
 *
 * 11.11f is on the CALLER and is not optional.  An agreement that FAILS and
 * one that returns an all-zero Z are the same event: OpenSSL fails the call,
 * CryptoKit throws, something else may return zeros.  Map either to
 * invalid_key (11.6b) — never to a transport error, and never retry it.
 * ppcp_rv_bootstrap_derive() catches the zero half; only the caller can see
 * the other half. */

/* ct = SHA-256("ppcp1 bs-commit" || pk_i) — 11.5b.  No key agreement. */
PPCP_API void ppcp_rv_bs_commit(const uint8_t pk_i[PPCP_RV_BS_KEY_BYTES],
                                uint8_t ct[PPCP_RV_BS_CT_BYTES]);

/* Constant-time compare, for 11.5d's commitment check and 11.5f's MACs.
 * Both are MUSTs and both are trivially got wrong with memcmp. */
PPCP_API bool ppcp_rv_ct_equal(const uint8_t *a, const uint8_t *b, size_t len);

/* Everything downstream of Z — 11.6c..11.6e — as one pure function. */
typedef struct ppcp_rv_bootstrap {
    uint32_t sas;                             /* 0..999999; render "%06u" (11.7a) */
    uint8_t  k_c   [PPCP_RV_KEY_BYTES];
    uint8_t  mac_i [PPCP_RV_BS_MAC_BYTES];
    uint8_t  mac_a [PPCP_RV_BS_MAC_BYTES];
    uint8_t  sid   [PPCP_RV_SID_BYTES];       /* version/variant bits set (11.6d) */
    uint8_t  prk   [PPCP_RV_KEY_BYTES];
    uint8_t  k_tls [PPCP_RV_KEY_BYTES];
    uint8_t  k_id  [PPCP_RV_KEY_BYTES];
} ppcp_rv_bootstrap;

/* `v` is 1..255 (11.4h1).  pk_i and pk_a are INITIATOR FIRST (11.6c): the
 * order is bound into the transcript, and transposing it is one of the six
 * causes RV §10.4 lists.  Fails for an all-zero `z` (11.6b) and for v == 0.
 * The transcript is bound into sas and k_c and into NOTHING else — 11.6c1,
 * and 11.6c2 forbids dropping pk_i||pk_a on the grounds that Z implies them.
 * The caller erases `z` and its own scalar afterwards (11.11h). */
PPCP_API ppcp_result ppcp_rv_bootstrap_derive(const uint8_t z[PPCP_RV_BS_KEY_BYTES],
                                              uint8_t v,
                                              const uint8_t pk_i[PPCP_RV_BS_KEY_BYTES],
                                              const uint8_t pk_a[PPCP_RV_BS_KEY_BYTES],
                                              ppcp_rv_bootstrap *out);
```

**Deliberately one call, not six.** `sas_raw`, `K_c`, the MACs, `sid`, `PRK`, `K_tls` and `K_id` all descend from `Z` and the transcript with no branching and no I/O between them. Splitting them would create six chances to bind the transcript into the wrong one — which is precisely [E40](../specification/ppcp-core.md#errata-after-revision-9) and [E43](../specification/ppcp-core.md#errata-after-revision-9), the two most serious findings in three review passes. One call, one transcript construction, one thing to get right, one thing for [RT-24a](../specification/ppcp-rv.md#9-conformance) to read.

## 5. What this note does **not** decide

- **The bootstrap frames.** Encoding and decoding `bs_offer` … `bs_abort` ([§11.4](../specification/ppcp-rv.md#114-frames)) is natural `libppcp` work — it owns the CBOR codec and the `PPCP-ENC` framing, and [E46](../specification/ppcp-core.md#errata-after-revision-9)'s unknown-key rejection belongs with the decoder. No surface is proposed here; it is a separate design and not what B17 asked.
- **The state machine.** [§11.5](../specification/ppcp-rv.md#115-the-exchange)'s five frames, the timeouts of [11.3e](../specification/ppcp-rv.md#113-roles-and-the-connection), the one-attempt rules of [11.3d](../specification/ppcp-rv.md#113-roles-and-the-connection) and [11.3d1](../specification/ppcp-rv.md#113-roles-and-the-connection) — all sockets and windows, therefore application work, per [A7](../implementation/implementation-plan.md) and [A8](../implementation/implementation-plan.md).
- **When any of it is built.** Nothing is scheduled. The programme is closed.
