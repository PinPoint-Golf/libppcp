# PPCP change request 02 — device status, onboard actuator control, and statistics visibility

| | |
|---|---|
| **Raised by** | Product requirement (PinPointCapture / PinPointStudio), 26 August 2026 |
| **Against** | `PPCP-CORE` 1.0 (revision 9, final), `PPCP-MSG` 1.0, both approved 22 August 2026, as amended by errata through E57 |
| **Type** | **Change request.** Not a defect — the specification is self-consistent and does not serve three requirements the product has acquired |
| **Tracked** | Not yet filed as an implementation issue in either application repository. This document is the request |
| **Reviewed** | [PinPointCapture](../specification/reviews/CR-02-review-PinPointCapture.md) and [PinPointStudio](../specification/reviews/CR-02-review-PinPointStudio.md), 26 August 2026. **Both support all three asks, no objection.** Six non-blocking findings between them, three from each team — tightened claims across all three sub-asks, one overstated gap (`readiness`/`interruption` already partially serve 3a), one miscardinalitied phrase (`Source.profiles` is mandatory, not merely useless if empty) — all incorporated below; none changed what is being asked for |
| **Status** | Open. Awaiting the protocol team's ruling. Nothing has been implemented ahead of it |

---

## 1. The ask, in one sentence

**PPCP needs a way for peers to share live device status beyond the phone's own battery and thermal state, a way for a host to command an onboard actuator (starting with the phone's torch) rather than only observe Sources, and a way to surface session-, device- and capture-ring-level statistics that today exist only as local, unshared numbers — and all three should be shaped to extend to a connected device class the specification has not yet met, such as a wrist sensor reporting swing metrics.**

That is three related asks, not one. §3 states each as its own requirement because each fails against the specification for a different reason, and a single clause will not answer all three.

---

## 2. What already exists — so this request is not read as reopening it

A reader who assumes none of this is carried today will over-ask. Some of it already is, and is out of scope here:

- **Peer-level battery, charging, thermal and storage already cross the wire.** `heartbeat_ack` carries `thermal`, `vendor_thermal_label`, `storage_free_bytes`, `battery_pct` (optional) and `charging` (optional) ([`PPCP-MSG` §5.4](../specification/ppcp-messages.md#54-heartbeat--heartbeat_ack)), and [`PPCP-CORE` 7.4b](../specification/ppcp-core.md#74-liveness) requires it. This is not being asked for again.
- **Per-shot capture statistics already exist.** `Capture.achieved_summary` carries frame count, drops, realised rate, exposure/ISO summary and a thermal timeline per capture ([`PPCP-CORE` §5.14](../specification/ppcp-core.md#514-capture)). This is not being asked for again — §3c below is about the *ring buffer* and the *session*, neither of which this covers.
- **A measurement of whether the next shot will settle is already carried, and it already reaches further than the phone's own battery report does.** `Readiness` ([`PPCP-CORE` §5.15](../specification/ppcp-core.md#515-readiness), [`PPCP-MSG` §5.2](../specification/ppcp-messages.md#52-arm--disarm--readiness)) answers "if armed now, will the first shot have settled exposure" — a different question from "is this device idle, ready, capturing or unavailable" and not being replaced — but it is an Event, direction **capture peer → any**, not host-only, and its `blocked_reason` already enumerates `storage_full`, `thermal_limit`, `permission_denied`, `no_source`. That is closer to 3a than `heartbeat_ack` is, and §4a is precise about the residual gap rather than treating this as absent.
- **A peer pushing its own status to whoever is listening already has one precedent.** `interruption` ([`PPCP-MSG` §5.3](../specification/ppcp-messages.md#53-interruption)) is an Event, **capture peer → any**, open-registry `kind`, reporting a platform condition that costs capture. It is scoped narrowly — to interruptions, not availability generally — but it is the existing shape closest to what 3a needs, not a message class that would have to be invented from nothing.
- **Extensibility to a future device class is already a solved problem for a passive Source.** `Source.kind` is an open registry ([`PPCP-CORE` §10.3](../specification/ppcp-core.md#103-registries)); a wrist sensor reporting samples fits today with no protocol change, the way `wrist` already appears as an example value ([`PPCP-CORE` §5.6](../specification/ppcp-core.md#56-source)). **What does not fit is a device that is *commanded*** — §3b and §4b explain why.

None of the above is reopened. §4 explains, for each of the three asks, exactly what gap remains once the above is subtracted.

**Both applications already carry their own local, unshared analogues of parts of this request**, independently arrived at — evidence this is a converged product need rather than a request in search of a mechanism. PinPointCapture's `RingStats` is real and computed but gated `#if DEBUG` and documented in its own codebase as *"an instrument, not a screen … deliberately not in the design handoff."* PinPointStudio has its own local "device status" concept (the Readiness strip in its UX design doc, showing connected devices, calibration ages and warnings) and its own ring-buffer UI (`CamerasPanel.qml`'s buffer bar, `resource_monitor_controller.cpp`'s `bufferState`). One clarification from review, worth recording so it doesn't read as evidence against the request: PinPointStudio already parses `heartbeat_ack`'s battery/thermal/storage fields but does not yet display any of them (`PpcpHostService::phones()` currently hardcodes `batteryPct: -1`) — a display backlog item independent of anything the protocol team rules on here, not a sign the wire content is insufficient.

## 3. The requirement

**3a — Device status, beyond the phone.** A host session should be able to show the operator, for every device that could plausibly be in the room — the phone, its cameras, its microphone, and (in future) a connected sensor — whether that device is `unavailable`, `ready`, `capture` or `idle`, and this picture should update live as devices come and go, without the host having to infer it from side effects. These four labels describe the operator-facing distinction wanted, not a proposed wire vocabulary — §4a and §5 discuss why they cannot cross the wire as written, and point at an existing precedent for a shape that could.

**3b — Command the phone's onboard light.** A host should be able to enumerate the onboard illumination the phone exposes, and turn it on and off, for the same reason the deployment [`E53`](../specification/ppcp-core.md#errata-after-revision-9) already confirmed generally: the operator stands at the host, physically apart from the phone, so lighting needed for exposure has to be adjustable from where the operator actually is. Two things this request leaves open rather than assumes: enumeration may legitimately come back empty for a given device (a front-camera-only setup, a phone with no rear flash), and whether "command" means on/off only or a continuous brightness level is a product decision, not one this request answers. This is asked as a first instance of a general shape: **a peer commanding an actuator on another peer**, not merely reading one — camera, microphone and torch today, and a connected device such as a wrist sensor's own indicator LED tomorrow, without a second protocol change per device class.

**3c — Session, device and ring-buffer statistics.** A host and a capture peer should each be able to see, live, the operating numbers that exist today only as unshared local counters: session-level aggregates (shots taken, captures committed, session duration so far), device-level aggregates (uptime this session, events or frames dropped, link quality such as throughput/offset/drift), and the capture peer's own ring buffer — how far back it currently reaches, how much of its retention window remains, when and how large its recent gaps or stalls have been, and how many segments it has already discarded before a host or a later export could reach them.

## 4. Why the specification does not serve it

### 4a — Device status

- **(2b) MUST NOT** *[`PPCP-MSG` §5.2](../specification/ppcp-messages.md#52-arm--disarm--readiness)* A device state-machine name cross the wire, restated from [`PPCP-CORE` 5.15a](../specification/ppcp-core.md#515-readiness): `cold`, `warm`, `armed` or any equivalent MUST NOT appear on the wire. **`unavailable` / `ready` / `capture` / `idle` is exactly the shape this clause forbids.** `Readiness` deliberately answers "would the next shot settle", a measurement, not "what state is this device in", a name — so 3a cannot be built as an extension of `Readiness` without contradicting the reasoning [`PPCP-CORE` §5.15](../specification/ppcp-core.md#515-readiness) gives for existing in that shape at all. Any answer to 3a either persuades the protocol team that a *device-availability* enumeration is a different kind of thing from the *device-state-machine* names 5.15a was written against, or is built as a further set of measurements in `Readiness`'s style. Which of those it should be is a design decision this request leaves open, per §6.
- **This is not a hypothetical risk — it has already happened three times independently, and none of the three agree.** PinPointCapture's own `CaptureState` is `cold`/`warm`/`armed`. PinPointStudio's own `BufferState` is `idle`/`capturing`/`paused`/`stopping`. This request's own §3a proposes a fourth, `unavailable`/`ready`/`capture`/`idle`. All three describe roughly "is this thing doing something right now," and none matches either of the others — concrete, present-tense evidence for exactly the platform- and app-shaped drift 5.15a exists to keep off the wire, not an abstract concern.
- **A working template for the shape 5.15a demands already exists and is shipping.** PinPointCapture's `Readiness` implementation answers a health callback with a *measurement* — `settled`, and an open-registry reason where it is not — never a state name, by its own design comment citing 5.15a directly. That is proof by construction that 3a's requirement is satisfiable without touching 5.15a: an `available` measurement plus an open `unavailable_reason` registry plus a "since when" or "ready in ms" figure, mirroring `Readiness`'s own shape, rather than the four-value enumeration §3a states informally. This is cited as an existing precedent for the protocol team to react to, not as a proposed field list — §6 still applies.
- **`heartbeat`/`heartbeat_ack` is Peer-scoped and host-initiated only.** Direction is fixed as `host → peer` for the request and `peer → host` for the reply ([`PPCP-MSG` §5](../specification/ppcp-messages.md#5-streams-and-capture-control) table). There is no per-`Source` status — a phone with a camera, a microphone and a future wrist sensor reports one battery and one thermal reading for the whole Peer, not one per device.
- **The residual gap, once `readiness` and `interruption` (§2) are subtracted, is narrower than "no path at all" and worth stating precisely so it cannot be under-answered.** Both are Live-profile, Stream-scoped Events, emitted only once a Stream is armed (`readiness`) or already capturing (`interruption`) — so a phone that is connected but not yet armed tells nobody anything, which is the actual gap. What remains unserved is: nothing before `arm`; nothing per-`Source` outside a Live-profile capture Stream; and no `idle`-vs-`capture` distinction, since `readiness`'s `settled` only ever answers whether the *next* shot would settle, not whether one is in progress right now.
- **`Source` carries no status field of any kind.** [`PPCP-CORE` §5.6](../specification/ppcp-core.md#56-source) declares what a Source *is* — `kind`, `timebase_id`, `profiles`, `calibration`, `optics`, `viewpoint` — entirely at declare time, and nothing in the model expresses whether a declared Source is, right now, capturing, idle, or unavailable (in use by another application, permission-denied, disconnected). `declare`/`declare_ack` ([`PPCP-MSG` §3.3](../specification/ppcp-messages.md#33-declare)) is not repeated once a session is open, so even the declare-time snapshot goes stale immediately.

### 4b — Onboard actuator control

**There is no gap to close incrementally here — the message set has no shape for this at all**, and that is worth stating plainly rather than found piecemeal:

- Every Request/Response pair in [`PPCP-MSG` §3](../specification/ppcp-messages.md#3-connection-and-declaration)–[§9](../specification/ppcp-messages.md#9-offline-export-and-reconciliation) either **declares** something the sender already is (`declare`, `hello`), **opens or closes data flow** the receiver already produces (`stream_open`, `arm`/`disarm`), or **carries data** one side already has (`payload_*`, `candidate`, `shot`). `arm`/`disarm` is the closest existing shape and it does not fit: it starts and stops a capture *Stream* that a Source already produces continuously — it does not change what a Source physically *does*, and a light is not a Source that produces samples at all.
- **`CaptureProfile` ([`PPCP-CORE` §5.7](../specification/ppcp-core.md#57-captureprofile)) is entirely about capture format** — `format`, `rate`, `optical`, `geometry`, `timing`, `intrinsics` — every field of which is meaningless for a torch. `Source.profiles` is cardinality `1..n` ([`PPCP-CORE` §5.6](../specification/ppcp-core.md#56-source)): at least one `CaptureProfile` is mandatory, not optional, so a light cannot be declared as a `Source` with an *empty* profile set — that declaration is already illegal, not merely useless. What a light forces instead is a `Source` whose one mandatory `CaptureProfile` has every field meaningless for what it is; the entity was built for something that produces frames, not something that is switched.
- **No message commands another peer's hardware in any direction.** The nearest thing, `arm`, is scoped to Live-profile capture Streams by [`PPCP-MSG` §5](../specification/ppcp-messages.md#5-streams-and-capture-control) and is not a general actuation primitive; extending its semantics to "turn this non-Stream thing on" would be exactly the kind of meaning-change [`PPCP-CORE` 10.2b](../specification/ppcp-core.md#102-extensions) forbids an extension from making, so this cannot be added as a `com.pinpoint.torch` extension either — it needs a core message class, or a deliberate decision that it does not belong in PPCP.

### 4c — Statistics

- **The capture ring buffer is real, tracked, and entirely local — and richer than "margin remaining."** `libppcp`'s own C API counts what its event ring drops (`ppcp_peer_events_dropped()`), and the capture peer's fragment ring buffer is where every shot-anchored `Capture` is extracted from ([`PPCP-CORE` Annex A.1 item 6](../specification/ppcp-core.md#a1-build-order), implementation plan pass H5). PinPointCapture's own local `RingStats` shows what an operator-facing view would actually inherit value from: frame- and fragment-drop counts broken out **by cause** (encoder busy, not retaining, write failed, empty), a `monotonicityViolations` counter, and an 8-bucket gap-duration histogram plus the 8 largest gaps carrying **both** how large and **when** each happened — added specifically after an incident where "how bad" without "where" was not enough to diagnose a stall. **None of it is expressed as a field anywhere in [`PPCP-CORE` §5](../specification/ppcp-core.md#5-data-model).** A host cannot ask a capture peer how far its buffer currently reaches back, let alone why it has been shrinking, and a capture peer cannot say so unprompted — the only way any of this surfaces today is retrospectively, as `absent_reason: outside_buffer` on a specific orphan capture request that already failed ([`PPCP-CORE` 8.4b](../specification/ppcp-core.md#84-orphan-capture-requests)), which tells a host what it already lost, not what margin it currently has or why.
- **`Session` carries no aggregate counters.** [`PPCP-CORE` §5.10](../specification/ppcp-core.md#510-session) lists `peers`, `timebase_ref`, `streams`, `shots`, `contexts`, `state`, `completeness` — the last of which is a completeness *assertion*, not a count. A host reconstructing "how many shots this session, how long has it run, how many captures are still `pending`" today must derive it by counting `Session.shots` and walking every `Capture.transfer` itself; nothing states it.
- **`Peer` carries no cumulative counters either, though both applications already compute some locally** — PinPointCapture's `TransferQueue` tracks `pendingShotIDs`, `bytesRemaining` and `currentShotOrdinal`; PinPointStudio's `HostLink` already surfaces throughput, clock offset and drift in its own telemetry UI, read locally rather than received from the peer. "Link quality" in 3c has a concrete existing shape to point to, not a placeholder word.
- **The session and device halves of 3c, and the ring-buffer half, are not the same shape, and an answer to one should not be assumed to answer the other.** Shots taken, session duration, uptime and drop counts are monotonic counters or settle-and-read values — the same shape as fields `Session` and `Peer` already carry, so this half is additive fields on entities that already exist. The ring-buffer margin is not: `video` Streams are `shot_windowed`, and [`PPCP-CORE` §5.11](../specification/ppcp-core.md#511-stream) is explicit that the ring buffer discards everything else and the capture stream is never materialised continuously — so the buffer sits **behind** the Stream abstraction, in no entity §5 currently models, and it changes on the same rhythm as `Readiness.settled` (every frame a phone sits idle-but-armed), which is why `Readiness` is a pushed, re-emitted Event rather than a declared field. The ring-buffer third of 3c is closer in kind to `Readiness` than to `Session.shots`, and the protocol team should be free to answer the two halves differently rather than read this request as asking for one field list.

## 5. The constraint any answer must respect

⛔ **13d is the one clause every part of this request has to clear.** *[`PPCP-CORE` 13d](../specification/ppcp-core.md#13-privacy-considerations)* **MUST NOT** PPCP carry telemetry; diagnostic export is user-initiated and out of band. Session-, device- and ring statistics shared *between the two paired peers actually running the session*, so the host can display them live and the operator can act on them, is not the same thing as telemetry leaving the session to a third party — but the distinction is exactly the kind of thing that reads differently in a clause than in the reasoning behind it, which is [`README.md`'s](README.md) own generalisation 3 from CR-01. Whatever is specified for 3c should say, explicitly, why it is not what 13d forbids, rather than leave a future reader to work it out.

⚠ **3a's naming has to be squared with 5.15a, not routed around it.** [`PPCP-CORE` 5.15a](../specification/ppcp-core.md#515-readiness) forbids a device state-machine name on the wire for a stated reason — a measurement is portable, a state name is platform-shaped. `unavailable`/`ready`/`capture`/`idle` was written into this request in exactly the vocabulary 5.15a exists to keep off the wire, and that may be the wrong vocabulary for the wire even where the underlying requirement is right. This request states the requirement (§3a) rather than presupposing its enumeration, on purpose.

⚠ **3b is a new capability class for this protocol, not an extension of an existing one**, and it changes the trust shape 4b's search came up empty against: today no peer can make another peer's hardware do anything, only observe what it already produces. [`PPCP-CORE` 12b](../specification/ppcp-core.md#12-security-considerations) already forbids accepting session control from an unauthenticated counterpart; whatever answers 3b should say explicitly whether an actuator command is session control for that purpose (this request assumes it obviously should be, but the specification does not yet say so for anything other than capture).

⚠ **Extensibility is load-bearing for all three**, not an afterthought — the request names a wrist sensor because a design that only reaches `unavailable`/`ready`/`capture`/`idle` for a phone's camera and torch, and a fixed set of session counters, will need a CR-03 the day a second device class ships. §10.3's open-registry pattern already does this well for passive Sources; whatever shape 3b takes should get the same property for actuators without the protocol team having to enumerate every future actuator kind in advance.

## 6. What this request deliberately does not propose

⛔ **No wire format, no message names, no field list.** It would be easy to sketch `device_status { peer_id, source_id, state }` and an `actuate` request/response pair here. It is left out on purpose, for the same reason CR-01 left its bootstrap mechanism out: a plausible-looking scheme arriving with a change request is harder to discard than no scheme at all, and 3a in particular has a real tension with 5.15a (§5 above) that a sketch would paper over rather than resolve. The design is the protocol team's.

⛔ **Nothing has been implemented.** Neither application ships any of this today; both ship `heartbeat_ack`'s existing battery/thermal/storage fields and nothing beyond them.

⛔ **No claim that all three parts are equally urgent, or must land together.** 3c is additive fields on entities that already exist. 3b is a new message class raising a new trust question. 3a sits in direct tension with an existing, deliberate clause. The protocol team may reasonably grant one, some or none independently — nothing here requires a single disposition covering all three.

---

## 7. If the answer is "no"

For 3a and 3c, that costs the product a display feature: an operator infers device readiness and session progress from what is already visible (arm state, shot count in the UI, storage warnings on `heartbeat_ack`) rather than from a purpose-built status view, exactly as both applications do today.

For 3b, "no" costs more: the light has to be operated at the phone, by whoever is standing next to it, which is the operator-walks-to-every-bay problem CR-01 §3 already described for pairing, recurring for a different reason. If the protocol team declines 3b, it is worth saying explicitly whether that is because actuator control does not belong in PPCP at all (a `PPCP-CORE` §1.3-style scope decision, the specification staying observation-only by design) or because this particular request has not yet made the case for it — the two are different answers with different consequences for whether a CR-03 in this direction is worth raising.

---

## 8. Questions this request would like answered explicitly

1. Is a live device-availability signal (3a) in scope for `PPCP-CORE` at all, given its tension with 5.15a — and if so, is it a new field on `Source` and `Peer`, a broadened `Readiness`, or something else?
2. Is commanding a peer's actuator (3b) a capability PPCP should carry, or is it a `PPCP-CORE` §1.3-style application concern — like UI — that this specification deliberately stays out of? If in scope, does it become a new message class alongside §3–§9 of `PPCP-MSG`, and is an actuator command session control for the purposes of [`PPCP-CORE` 12b](../specification/ppcp-core.md#12-security-considerations)?
3. Is session/device/ring statistics visibility (3c) distinguishable from the telemetry 13d forbids in a way the protocol team is willing to state normatively — and if granted, does it live on `Session` and `Peer` as additive fields, or as a new polled/pushed message?
4. Whichever way 3b is answered, should the registry pattern of [`PPCP-CORE` §10.3](../specification/ppcp-core.md#103-registries) extend to actuator kinds the way it already does to `Source.kind`, so a future connected device's indicator or vibration motor does not need its own change request?
