## 1. Can PinPointStudio actually support this? Grounded against the real code, not the last review's claims.

This round is stricter than the last one on purpose — a clause can be wrong in ways a requirement can't, and the disposition's §6 asked six specific questions of this codebase. Answering them directly, in the disposition's own order:

**§6 ask 1 — is `DeviceStatus` actually distinguishable from `Readiness`, or would we compute both from the same check?** Distinguishable, and the real code shows why. `PpcpHostPeer::readiness()` (`src/Ppcp/ppcp_host_peer.cpp:67-110`) is peer-wide and holistic: it checks storage pressure, thermal state, and whether the peer has declared any Source at all, in that order, and returns `settled` otherwise — it has no per-Source parameter and never asks "is *this* camera specifically in use by another process, or permission-denied, or disconnected." `DeviceStatus.reason`'s vocabulary (`in_use`, `permission_denied`, `disconnected`, alongside `thermal_limit`/`storage_full`/`no_source`) needs genuinely new plumbing — the kind that lives in `DeviceEnumerator`/`CameraManager` territory for local cameras today and does not exist at all for a PPCP-declared Source. **On a single-camera phone**, the two platform checks (storage, thermal) that both `readiness()` and a future `device_status` emitter would consult are likely to share the same underlying reading — that's expected overlap, not a design flaw: `Readiness` answers "once armed, will the shot settle," `DeviceStatus` answers "can this be opened at all, before arm," and a phone that is thermally throttled answers both questions the same way for the same reason. 5.20b's independence claim holds.

**§6 ask 2 — is host-only `actuator_command` scoping (12a) right for a Studio deployment?** Yes, with no real counter-case in this codebase. PinPointStudio is always `role: host` and every capture peer is a direct, individually-authenticated link to it (star topology, one `PeerConnection` per phone) — there is no plan, shipped or designed, where one paired phone would need to command another phone's torch, and the multi-phone work already shipped (`[[ppcp-pair-button]]`, several phones concurrently) never routes anything peer-to-peer; everything flows through the host. Nothing here motivates a CR-03.

**§6 ask 3 — does §2c's "already served" table hold against how PinPointStudio actually retains capture data?** No — not today, though this does not mean the decline itself is wrong. See **R-2**.

**§6 ask 4 — does `BufferMargin`'s shape (single `last_discard`, no histogram) match what the local instrumentation would need?** Yes, and it maps onto an idiom this codebase already uses twice, but it does not feed either of the two things a reader would guess it should. See **R-4**.

**§6 ask 5 — is `actuator_command_ack.state` echoing the achieved value buildable, and can a torch's clamping be observed?** Out of this codebase's scope to answer directly — PinPointStudio only ever *originates* `actuator_command`; it never owns an Actuator itself (§2.2.3's worked example: "commands one," never "owns one"), so it has no torch driver to query for clamped output and cannot confirm PinPointCapture's platform behaviour. What PinPointStudio's own code *can* say is in **R-1**: regardless of what a phone's driver can observe, nothing in the message shapes currently constrains what `state` may legally contain once it arrives, which is a gap independent of any platform's clamping behaviour.

**§6 ask 6 — does `PpcpHostService::phones()`'s hardcoded `batteryPct: -1` block anything in this grant?** Confirmed still present, unchanged, at `src/Ppcp/ppcp_host_service.cpp:869`. It is exactly the pre-existing display backlog item my prior review named and nothing more — `PpcpLiveSession::peerHealth().batteryPct` (`ppcp_live_session.cpp:260`, populated from `heartbeat_ack`) sits one call away and unread, same as before. It does not block `DeviceStatus` or `BufferMargin`, which arrive through entirely separate messages and would need their own new plumbing regardless of whether this one field ever gets wired up.

**One correction of my own prior review, since the disposition quotes it directly (§2, in the "already right" section) and the task explicitly asks whether it still holds.** My prior review said `HostEngineConfig`'s one-slot-per-concern design (`health`, `healthReport`, `syncTimebase`) "accommodates a new actuator-command slot the same way it accommodated the others." **Against the real messages, this does not hold, and the reason is structural rather than a detail.** `health` and `healthReport` are *inbound* callbacks: libppcp calls back into the host, synchronously, to answer a request the *counterpart* sent (a `readiness` check, a `heartbeat`). `actuator_command` is the opposite shape for a host: it is a request *this host originates*. The actual precedent in this codebase for a host-originated request is not a `HostEngineConfig` slot at all — it is a direct method on the class that owns the conversation, calling straight into libppcp's C API: `PpcpLiveSession::arm()`/`disarm()` (`ppcp_live_session.cpp:295,318`) call `ppcp_peer_arm()`/`ppcp_peer_disarm()` directly, and `VideoInputPpcp::start()` calls `ppcp_peer_stream_open()` directly (`VideoInputPpcp.cpp:582`). Neither goes anywhere near `HostEngineConfig`. So the real shape of the work is: a new `ppcp_peer_actuator_command()` in libppcp's C API (not yet present — `include/ppcp/*.h` has no `actuator` symbol anywhere, expected since this is freshly specified), a new outbound method alongside `arm()`/`disarm()` on `PpcpLiveSession` (or a sibling class) to send it, and an inbound path for `actuator_command_ack`/`actuator_state` shaped like the existing `PeerHealth`/`setHealthCallback()` pattern rather than a config callback. This is buildable, and is not materially harder than `arm`/`disarm` was — but it is a different pattern than the one my own prior review pointed at, and a reader building from that review's claim would look in the wrong file first.

**A smaller, related gap:** PinPointStudio's own declared-profiles list is a hardcoded static vector — `PpcpSourceDeclaration::studioProfiles()` (`ppcp_source_declaration.cpp:261-270`) — currently `{"core", "capture", "detect", "arbitrate", "live", "offline", "markup"}`, with no `"actuate"`. This is expected (nothing is implemented yet) and not a spec defect, but it means Studio's own worked-example row in §2.2.3 ("PinPointStudio host … + Actuate, commands one") is not yet true of the code and the omission is easy to miss precisely because `Peer.actuators` is legally `0..n` and a host with no Actuators of its own "participates fully" either way (5.19c) — nothing will visibly break if `"actuate"` is forgotten from that list; `actuator_command` will simply be silently unavailable to originate (C2), with no test in this codebase to catch the gap until someone tries to use it.

## 2. Findings

### R-1 — I39 constrains only `actuator_command`; the two messages that carry the achieved state have no equivalent constraint

I39: *"An `actuator_command` carries `on` if and only if the named Actuator's `control` is `on_off`, and `level` if and only if it is `level` — never neither, never both."* This is precise, and 12.1a correctly makes a mismatched `actuator_command` `malformed`.

**But `actuator_command_ack.state` and `actuator_state.state` carry the identical `{ on: bool (optional), level: float (optional) }` shape, and nothing anywhere binds their presence to the named Actuator's `control` the way I39 binds the request.** 12.1c says `state` reports the achieved value rather than an echo, and describes clamping — but says nothing about which of `on`/`level` may legally be present. 12.2 (`actuator_state`) says even less: no clause states whether an on/off-only Actuator's `actuator_state.state` may legally carry a `level`, or none of either.

This is not a hypothetical: it is exactly the shape of defect I39 itself exists to prevent, one message later. A conformant phone implementation could report `state: { on: true, level: 1.0 }` for a torch declared `control: on_off` — defensively including both "for completeness" — and nothing in this specification makes that malformed. Another conformant implementation, receiving it, has to decide for itself whether to trust `level` on an `on_off` Actuator, because the spec gives it no rule to check against. **Two conformant implementations, no way to interoperate on what `state` means once it says something the sender's own `control` declaration forbids** — precisely the "produce two implementations that can't interoperate" category this review is asked to prioritise.

**Fix:** extend I39 (or add I39a) to state that `actuator_command_ack.state`, where present, and `actuator_state.state` carry `on` if and only if the named Actuator's `control` is `on_off`, and `level` if and only if it is `level` — on the same terms as the request. Add a normative bullet under both 12.1 and 12.2 restating it locally, the way 12.1a does for the request. This is a text-only fix and CT-I39 (or a sibling test) can assert it the same way it already asserts the request's shape — confirmable in round 2 by re-reading the amended clause; it does not need a round 4.

### R-2 — §2c's "already served" argument for shots/captures/drops does not hold against PinPointStudio's actual retention today, though this does not mean the decline itself is wrong

Checked directly (fork of this review, against `src/Ppcp/` and `src/Video/VideoInputPpcp.cpp`), the disposition's §6 ask 3 in mind: **PinPointStudio does not retain per-Capture `transfer`/`achieved_summary` state such that `Capture.transfer == confirmed` could be walked after the fact. It cannot walk it today at all, for a reason stronger than "not yet wired to a UI":**

- `PPCP_MT_CAPTURE_UPDATE` — the message that would carry a later `transfer` state (`pending` → `in_flight` → `present` → `confirmed`) after the initial `capture_announce` — is **never dereferenced anywhere in `src/`**, only in libppcp's own header. `PpcpShotBridge::observe()` (`ppcp_shot_bridge.cpp:190-238`) switches on candidate/shot/relation/capture-request events and does not handle `PPCP_EVENT_CAPTURE` at all.
- The one place a Capture is actually processed, `VideoInputPpcp::onCaptureAnnounce()`/`deliver()` (`VideoInputPpcp.cpp:872-1032`), reads `achieved_summary` only to validate and gate, folds nothing into a retained field, and resets its open-capture state immediately after emitting `clipReady(clip)` — a signal that is **explicitly, deliberately not connected** in production (`ppcp_host_service.cpp:105-114`, blocked on the `Session.id`/`Shot.id` identity mismatch `[[ppcp-host-work]]` item 2 already names). `PpcpClip` itself carries no `achieved_summary` field to retain even if something did connect it.
- The only PPCP-derived counters that exist (`PpcpShotBridge::Stats`, `VideoInputPpcp::Counters`) are running scalars read only from tests, not exposed anywhere a UI or a stats query could reach them.

**This is not a reason to reopen E61.** The wire content genuinely is there — `capture_announce`/`capture_update` are `owner → any`, exactly as §2c states — and nothing stops PinPointStudio from building the retention this argument assumes. The honest correction is about **cost, not correctness**: unlike `heartbeat_ack`'s battery field (a scalar sitting one call away, per the R in §1 above), walking `Capture.transfer`/`achieved_summary` needs a live Capture ledger that does not exist at all, plus parsing a message class (`capture_update`) this codebase currently ignores outright. The disposition's own framing — "a display backlog item independent of anything the protocol team rules on" — undersells this one relative to battery. **Verdict, as the disposition's §6 asked for directly: the decline stands; the wire content is sufficient in principle.** But a future reader should not assume this is a small follow-on the way the battery field is — it is closer in size to the `capture_announce` handling PinPointStudio already has than to a one-line wire-up, and should be sized accordingly whenever it is actually built.

### R-3 — `DeviceStatus`'s per-Source scoping will re-expose a pre-existing identity collision if the fix isn't carried along

`Source.id` is `"Unique within the owning peer"` (§5.6), and `device_status` is scoped to `source_id` — correct and unambiguous on the wire. But PinPointStudio's own device-identity keying for a PPCP camera does **not** currently use `Source.id`: `serialNumber` is set to the owning peer's id for every PPCP camera (`VideoInputPpcp.cpp`, noted at `resource_monitor_controller.cpp:161-170`), and the historical/folded-stats lookup key `camIdent` (`resource_monitor_controller.cpp:228`) falls back to that `serialNumber` whenever it's non-empty — which for a PPCP camera it always is. **Two cameras on one phone therefore already share one identity for folded lifetime stats**, a defect the project's own memory already records as pre-existing and open.

`device_status` arriving per-`source_id` for a two-camera phone will hit exactly this seam if a future UI keys its `device_status` handling off the same `camIdent`/`serialNumber` pattern rather than off the wire's actual `source_id`: two Sources' live availability would collide onto one displayed row, silently, the way the folded byte/event counts already do. This is not a spec defect — the wire already carries what's needed — but it is a real, concrete "does anything conflict with how PinPointStudio actually works today," and worth naming before the first implementation pass repeats the existing bug in a second place. **Fix:** any `device_status` consumption on the PinPointStudio side should key on the wire's `source_id` directly (which libppcp already guarantees unique per peer), never on `serialNumber`/peer-id-derived `camIdent`.

### R-4 — `BufferMargin`'s shape is buildable and right-sized, but it doesn't feed either existing "buffer" concept in this codebase — it's new UI, not a rewire

Checked against the two things a reader would guess `BufferMargin`/`buffer_status` should map onto, and neither is actually it:

- **`CamerasPanel.qml`'s "Ring buffer bar"** (`CamerasPanel.qml:1617-1672`, `storageRect.ringPct`) is a **static, config-time storage-cost ratio** for a local camera — `ringBytes / ringFullBytes` (ROI-cropped bytes vs. full-frame bytes, both × a fixed `fps × 5s` slot count) — answering "how much does this crop save," not "how full is the buffer" or "how far back does it reach." It never varies live and has no notion of "since" or "discarded."
- **`resource_monitor_controller.cpp`'s `ringFill`** (`events_written / slot_count`, line 236-238) is the **host's own local, post-receipt** occupancy of frames it has *already decoded and buffered locally* for a Source — the mirror image of what `BufferMargin` reports. `bufferState` (Idle/Capturing/Paused/Stopping, line 46-53) is a single session-wide state, not per-Source either.

**Neither is what `BufferMargin` answers**, which is the *phone's own, pre-transfer, upstream* ring margin — a quantity PinPointStudio currently has **zero visibility into**, confirmed by `[[ppcp-host-work]]` item 4: `EventBuffer::reserveSourceId()` is deliberately unbuilt for a phone-hosted sensor, and nothing today connects a remote peer's own buffer state to anything on the host side. So `BufferMargin` isn't answering a question this codebase already half-displays; it's opening one that was previously invisible entirely.

Given that, the shape holds up well on its own terms: `retained_from` + `retention_target` reduce to exactly the same `elapsed / target → percentage` idiom this codebase already uses twice (the ratio above, and `ringFill`), so a new per-Source margin gauge is a small, idiomatic addition once the plumbing to receive `buffer_status` exists at all. **Direct verdict on the disposition's own question:** the single `last_discard` (not a histogram) is sufficient. A studio session runs a phone over a local link the operator is standing next to; the operator's actionable response to a stall is "move closer to the router" or "close the other app," not a distribution of gap sizes — the histogram PinPointCapture's `RingStats` carries answers an engineering diagnostic question this deployment doesn't need answered live. Keep it as specified.

## 3. What's already right and doesn't need touching

- **E59's `DeviceStatus` genuinely earns its "not derivable from `Readiness`" claim (5.20b) against the real host code** — `PpcpHostPeer::readiness()` checks nothing per-Source and would need new plumbing entirely separate from itself to answer `DeviceStatus`'s question. This is confirmed, not assumed.
- **E60's `BufferMargin` shape (no histogram) is the right call**, confirmed against both of this codebase's existing buffer-adjacent UI concepts and the deployment `BufferMargin` actually serves — see R-4.
- **Host-only `actuator_command` scoping (12a) has no counter-case in this codebase.** PinPointStudio's star topology (host, direct authenticated links, no phone-to-phone traffic anywhere) doesn't motivate widening it, now or foreseeably.
- **12d's "actuator_command is session control" costs nothing extra to implement here.** Every host-originated request already flows over the same authenticated `PeerConnection`/TLS-PSK link that gates `arm`/`disarm`/`stream_open` today; there is no separate trust boundary to build.
- **5.19b's Source/Actuator disjointness matches the codebase's own model cleanly.** `PpcpSourceDeclaration`'s builder is entirely camera/microphone-shaped (`profiles`, `calibration`, `optics`); nothing in it could accidentally declare a torch as a zero-profile Source even by mistake, because the builder has no path that produces an empty `profiles` list at all.
- **E62/13e's telemetry carve-out is correctly scoped** and matches how this application already treats `heartbeat_ack`'s health data — read only by the peer it came from, for the session it's running, never relayed elsewhere.

**Also corrected in §1, not tabled as a finding:** my prior review's claim that `HostEngineConfig`'s callback-slot design accommodates a new actuator-command slot "the same way it accommodated the others" does not hold against the actual message shapes. The real precedent for a host-originated request in this codebase is a direct method calling libppcp's C API (`PpcpLiveSession::arm()`/`disarm()`, `VideoInputPpcp`'s `ppcp_peer_stream_open()`), not a `HostEngineConfig` slot — `health`/`healthReport`/`syncTimebase` all answer *incoming* requests, and `actuator_command` is the opposite direction. Buildable, not materially harder than `arm`/`disarm`, but a different file than the one my own prior review pointed at.

**None of R-2, R-3 or R-4 needs a spec change.** Only R-1 does, and it is small, precisely scoped, and confirmable without a fourth round.
